差分を「他人の目」で読み直し、気付ける範囲のレビュー指摘を先回りで処理します。

## いつ使うか

- PR を出す直前。
- ドラフト PR を ready for review に切り替える前。
- レビュー前にセルフチェックリストを通したいとき。
- **使わない**: コミット前段階（→ `checking-commit`） / 他人の PR レビュー（→ `code-reviewer` agent）。

## 進め方

1. **必要情報をヒアリング** — `AskUserQuestion` で順次。最初の指示に含まれている項目はスキップ。納得まで掘り下げ可。1 ラウンドあたり最大 4 質問のため、項目が多い場合は複数ラウンドに分ける:
   - **対象ブランチ**: 現在のブランチ / 指定ブランチ
   - **比較先**: `main` / `develop` / その他
   - **観点重み**: 全部均等 / 性能重視 / セキュリティ重視 / 可読性重視
   - **追加観点**: a11y / パフォーマンス / 後方互換 / エラーハンドリング
   - **事前情報**: 関連チケット ID / 想定レビュアー / 急ぎ度

2. **差分を取得**:
   ```bash
   git diff <base>...HEAD --stat       # 概要
   git diff <base>...HEAD               # 全差分
   git log <base>..HEAD --oneline       # コミット履歴
   ```

3. **観点別にチェック**:
   - **命名**: 意図が伝わる名前か。略語の濫用、意味のない `data` / `info` / `manager`
   - **設計**: 単一責任、不要な抽象、漏れている境界
   - **テスト**: 網羅性、エッジケース、テストの可読性、テストが「実装」を見ていないか
   - **性能**: N+1、不要な再レンダー、O(n²) の潜在
   - **セキュリティ**: 入力検証、認可チェック、シークレットの埋め込み、SQL/XSS
   - **後方互換**: 公開 API / DB スキーマ / 設定形式
   - **エラーハンドリング**: 握りつぶし、型情報の欠落、ユーザー向けメッセージ
   - **コメント**: 「なぜ」が必要な箇所に「何」を書いていないか / 不要なコメント

4. **重大度別にグルーピング**:
   - `[blocker]` PR を止めるべき
   - `[important]` PR 内で直すべき
   - `[nit]` 任意・好み
   - `[praise]` 良い点（水増ししない）

5. **成果物を `.claude/output/reviewing-own-changes/<YYYY-MM-DD-HHmm>-<branch>.md` に書き出し** — 標準出力には blocker / important のみ。

## 出力フォーマット

```markdown
# Self-review: <branch>

## サマリ
- 変更ファイル: <N>, +<X> / -<Y>
- 観点重み: <設定値>

## [blocker]
- **<file:line>** — <問題> → <修正案>

## [important]
- **<file:line>** — <問題> → <修正案>

## [nit]
- **<file:line>** — <提案>

## [praise]
- **<file:line>** — <良い点>

## チェックリスト
- [ ] テストは新しいコードパスを通っているか
- [ ] エラーケースのテストがあるか
- [ ] 後方互換性は壊れていないか
- [ ] セキュリティ観点（入力検証 / 認可）は OK か
- [ ] コミットメッセージは PR タイトル候補として通用するか
```

## ルール

- **指摘は file:line で引用**。「全体的に〜」は避ける。
- **修正案を必ず添える**（blocker / important）。指摘だけは無価値。
- **水増ししない**。問題がなければ「問題なし」と書いて終わる。
- **自分が書いたコードへの遠慮を排除**。他人の差分のつもりで読む。
- 修正は自動実行しない。`/loop` などで実装段階に渡す。
